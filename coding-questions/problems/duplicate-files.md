# Find Duplicate Files

从 `/` 开始遍历一个模拟的文件系统，找出内容完全相同的文件组（每组至少 2 个）。文件内容只能通过
`openStream(path)` 拿到二进制流，文件最大 10⁹ 字节，文件数最多 10⁶。可以假设标准哈希没有冲突。

| 版本 | 要求 | 方法 |
|---|---|---|
| base | 返回所有重复文件组 | `findDuplicateFiles()` |
| FU1 | 每次 `read` 最多读 `limit` 字节，不能把大文件整个读进内存 | `findDuplicateFiles(int limit)` |

`FileSystem`（`src/duplicatefiles/FileSystem.java`）是模拟的文件系统，API 跟题目一致。它额外记录了
读了多少字节、单次 `read` 最多要了多少、打开了几次文件，测试用这些数字检查 `limit` 和 I/O 量。

## 思路

- **base**
  1. 用栈做迭代 DFS 遍历目录树（不用递归，目录很深也不会栈溢出），**先按文件大小分组**。
     大小不同的文件不可能重复，而 `getFileSize` 不用读内容。只有一个文件的大小组直接跳过，这些文件一次都不会打开。
  2. 大小相同的文件，用固定 8 KB 缓冲区流式读完，算 SHA-256，再按哈希分组。
- **FU1：三轮过滤，越往后越贵，参与的文件越少**
  1. 按大小分组（不读内容）。
  2. 按**第一块**（最多 `limit` 字节）的哈希分组。大部分不同的文件在这里就分开了，只读了很少的数据。
  3. 还撞在一起的，才读完整个文件算哈希；如果文件不超过 `limit` 字节，第一块就是整个文件，不用再读一遍。

  每次 `read` 请求的字节数都不超过 `limit`；缓冲区大小是 `min(limit, 1 MB)`，`limit` 很大时也不会占太多内存。

## 要提的点

- `listFiles` 返回的是名字还是完整路径，题目没说。代码两种都能处理（`join`）。
- `read` 可能返回比请求少的字节数，所以要循环读，按实际返回的 `n` 更新哈希。
- 如果不能假设哈希无冲突：哈希相同的文件再逐块比较字节，确认真的相同。
- 文件数 10⁶ 时，路径和大小放在内存里没问题；如果更大，可以把 `(大小, 路径)` 写到磁盘上外部排序再分组。
