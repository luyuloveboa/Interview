# System design

Step-by-step designs: short requirements, API and data model, then a baseline high-level design and one deep dive per step. Each step redraws the full diagram; new or changed parts are outlined in orange.

| Design | Core requirements | Steps | Files |
|---|---|---|---|
| [Payment system](payment/README.md) | 1. Merchant creates a payment intent<br>2. Customer pays it by card (3DS if needed)<br>3. Check a payment's status<br>4. List transaction history | 8 | [Markdown](payment/README.md) · [PDF](payment/payment.pdf) |
| [ChatGPT](chatgpt/README.md) | 1. Users should be able to send a prompt in a chat and receive an AI-generated response<br>2. Users should be able to view past chats and resume a conversation, with the chat's prior context carried into the prompt | 7 | [Markdown](chatgpt/README.md) · [PDF](chatgpt/chatgpt.pdf) |
| [Google Docs](google-docs/README.md) | 1. Users should be able to create new documents<br>2. Multiple users should be able to edit the same document concurrently<br>3. Users should be able to view each other's changes in real time<br>4. Users should be able to see the cursor position and presence of other users | 7 | [Markdown](google-docs/README.md) · [PDF](google-docs/google-docs.pdf) |
| [Ticketmaster](ticketmaster/README.md) | 1. Users should be able to view events<br>2. Users should be able to search for events<br>3. Users should be able to book tickets to events | 6 | [Markdown](ticketmaster/README.md) · [PDF](ticketmaster/ticketmaster.pdf) |
| [Online Chess](online-chess/README.md) | 1. Players should be able to find an opponent through skill-based matchmaking and start a game<br>2. Players should be able to play a game in real time<br>3. Players should be able to view a global leaderboard and see their own rank, both updating shortly after games finish | 6 | [Markdown](online-chess/README.md) · [PDF](online-chess/online-chess.pdf) |
| [Metrics Monitoring](metrics-monitoring/README.md) | 1. The platform should be able to ingest metrics (CPU, memory, latency, custom counters) from services<br>2. Users should be able to query and visualize metrics on dashboards with filters, aggregations and time ranges<br>3. Users should be able to define alert rules with thresholds over time windows (e.g. "alert if p99 latency > 500 ms for 5 minutes")<br>4. Users should receive notifications when alerts fire (email, Slack, PagerDuty) | 7 | [Markdown](metrics-monitoring/README.md) · [PDF](metrics-monitoring/metrics-monitoring.pdf) |
| [Bitly](bitly/README.md) | 1. Users should be able to submit a long URL and receive a shortened version<br>2. Users should be able to access the original URL by using the shortened URL | 5 | [Markdown](bitly/README.md) · [PDF](bitly/bitly.pdf) |
| [Dropbox](dropbox/README.md) | 1. Users should be able to upload a file from any device<br>2. Users should be able to download a file from any device<br>3. Users should be able to share a file with other users and view the files shared with them<br>4. Users can automatically sync files across devices | 6 | [Markdown](dropbox/README.md) · [PDF](dropbox/dropbox.pdf) |
| [Yelp](yelp/README.md) | 1. Users should be able to search for businesses by name, location (lat/long) and category<br>2. Users should be able to view businesses (and their reviews)<br>3. Users should be able to leave reviews on businesses (mandatory 1–5 star rating and optional text) | 5 | [Markdown](yelp/README.md) · [PDF](yelp/yelp.pdf) |
| [Local Delivery Service](local-delivery/README.md) | 1. Customers should be able to query availability of items, deliverable in 1 hour, by location (the effective availability is the union of all inventory in nearby distribution centers, DCs)<br>2. Customers should be able to order multiple items at the same time | 5 | [Markdown](local-delivery/README.md) · [PDF](local-delivery/local-delivery.pdf) |
| [Rate Limiter](rate-limiter/README.md) | 1. The system should identify clients by user ID, IP address, or API key to apply appropriate limits<br>2. The system should limit HTTP requests based on configurable rules (e.g., 100 API requests per minute per user)<br>3. When limits are exceeded, the system should reject requests with HTTP 429 and include helpful headers (rate limit remaining, reset time) | 5 | [Markdown](rate-limiter/README.md) · [PDF](rate-limiter/rate-limiter.pdf) |
| [Web Crawler](web-crawler/README.md) | 1. Crawl the web starting from a given set of seed URLs<br>2. Extract text data from each web page and store the text for later processing | 5 | [Markdown](web-crawler/README.md) · [PDF](web-crawler/web-crawler.pdf) |
| [Job Scheduler](job-scheduler/README.md) | 1. Users should be able to schedule jobs to be executed immediately, at a future date, or on a recurring schedule (i.e. "every day at 10:00 AM")<br>2. Users should be able to monitor the status of their jobs | 5 | [Markdown](job-scheduler/README.md) · [PDF](job-scheduler/job-scheduler.pdf) |
| [Ad Click Aggregator](ad-click-aggregator/README.md) | 1. Users can click on an ad and be redirected to the advertiser's website<br>2. Advertisers can query ad click metrics over time with a minimum granularity of 1 minute | 5 | [Markdown](ad-click-aggregator/README.md) · [PDF](ad-click-aggregator/ad-click-aggregator.pdf) |
