# AI Coding 通用规则（F1–F13 精简版）

> 来源：Hello Interview AI Coding 课程 Fundamentals 五篇，规则 F1–F13。
> 核心一句话：**你是指挥，AI 是打字员，面试官要听到你的决策。**
> 默认面试 AI 是 **nerfed 的**——更可能是面试工具缺日常版内置的 system prompt 与上下文，而非故意削弱；Meta 候选人反馈明显弱于练习版、Uber 只给 nudge 不给解、可能不直接指 bug、回答 cryptic 或拒绝某些请求。平时练就要按“受限 AI”练。

## 七条通用规则（背下来）

### R1 指挥权在你：AI 管体量，你管判断
- approach、数据结构、edge case 的选择全归你；AI 提 approach 可以，但要权衡后有理由地选一个，不能照单全收。
- AI 只做 boilerplate、陌生语法解释、基础脚手架；hard thinking 自己扛。
- 高风险处（auth / 支付）放慢细审；不熟的代码库区段更要问得具体。

### R2 先读后问：先自己读 5–10 分钟定向，再问 AI
- 定向顺序：入口 → 核心函数 → 类和数据模型 → 架构模式 → 公共 / 私有接口 → 状态管理 → 已有测试。
- 再问 AI **具体问题**，别只说“解释这段代码”：
  - “这个函数是干嘛的，一句话说”
  - “数据从哪来、到哪去”
  - “这个分支什么时候触发”
- 让 AI **标行号**，关键结论你自己对着原文核一遍。
- 三个坑：AI 会读错（尤其边界条件、隐式约定、并发逻辑）；AI 会把“应该做什么”说成“在做什么”；直接跳去 prompt、整库倾倒，是面试官眼里可见的失败信号。

### R3 计划 + 测试先行：先定验收标准，再动手
- 写 prompt 前定好 done 的验收标准；用 Understand → Plan → Execute → Validate。
- 计划里三个谈资点：**tech stack、数据模型 + API 契约（先行于功能）、testing strategy（先定，AI 才生得出有用测试）**。
- 测试是规格不是事后补票：先和面试官对齐测试用例（输入与期望输出），对齐“正确”与“完成”的定义。先失败，失败测试就是给 AI 的靶子。
- 好测试七类：happy path、空 / 零、单元素、边界值、重复、非法 / 意外输入、规模（性能题加大输入防超时）。不用每函数全套，但过一遍清单再往下走。

### R4 Prompt 要准：what + how 给清，syntax 留给 AI
- 粒度是执行期最大杠杆。甜点 = 给清 what + how、把 syntax 留给 AI（例：实现 trie，支持 insert 与 prefix search，节点存字符 + end-of-word 布尔值——思路钉死、写法不管）。
- 难度匹配具体度：复杂状态机等 tricky 逻辑要讲精确（approach、数据结构、约束）；boilerplate / 重复代码短而模糊即可，反正会验。
- 用代码库里的类名、方法签名、数据结构点名（例：给 Dictionary 类加 searchByPrefix，用现有 TrieNode 结构、返回 `List<String>`）。不带上下文的通用 prompt 产出的代码能跑但会和架构冲突。
- 主动要简洁输出（be concise / minimal comments），多余行数全是 review 与 defend 成本。

### R5 小步验证：每次生成后跑起来，不在 broken code 上叠代码
- 不叠多个改动再编译——单看都对、合起来可能 cascade 报错。修好 breakage 再往下。
- 静态类型语言里保持编译 + 类型干净就是增量验证；每次生成后都编译 / typecheck，类型错误直接丢给 AI（“Fix the type error on line 42”比“something seems wrong”好得多）。
- 测试没覆盖的 AI 行为默认不许；“能跑”≠验证过。改完回归全套。
- 每阶段 / 里程碑后都跑测试 + 编译，不要攒到最后。

### R6 坏输出只修一次 + 找 bug 先复现
- 30 秒能手改完的绝不 prompt；坏输出**重 prompt 最多一次**，之后手改或换路；不给 90% 对的输出打补丁（改计划让它重生）；单点跟 AI 纠缠超 2 分钟就自己写。
- 验收前先扫四类坏输出：① training bias——教科书 LeetCode 解技术上对但不 fit 本题约束；② verbosity——150 行 where 60 行够；③ design shortcuts——无意义父类、深继承、两处共享就上 strategy pattern；④ correctness shortcuts——删 failing test、any 绕类型、try/catch 吞异常、hardcode 特定用例、无谓 cast、忽略 nullability，全是面试官眼里的红旗。
- **找 bug 绝不宽泛问“帮我找 bug”**（Meta 的 AI 被设成不主动指 bug，它说没看到问题 ≠ 没问题；太宽泛的问法只能泛泛扫一遍，容易漏真 bug 或编假 bug）。正确打法：
  1. 先自己读函数，跑测试复现失败；
  2. 带着三样东西去问：输入 / 预期 / 实际，再加失败输出；
  3. 再加你自己的怀疑：“我怀疑是这里 off-by-one / 条件反了，你帮我确认一下”。
  - 例：“function1 输入 X，预期是 Y，实际是 Z，测试在第 N 行失败，输出是…，我怀疑是循环边界有问题，帮我看看这段逻辑。”
  - 注意：Meta 第一阶段有时禁用 AI 修 bug，bug 本身就得你自己能找；平时练也别养成只靠 AI 找 bug 的习惯。
- 调试找根因不打补丁掩症状；debug 工具（断点 / watch / 调用栈）优先于猜测，堆栈从上往下读框架帧。

### R7 全程出声：双线对话，决策要讲
- AI 面试里你同时管两条对话（和 AI、和面试官），面试官看得见 prompt 和输出、看不见你的思考过程，不出声就没法评估你的决策。
- 节奏 = 先说意图、再 prompt、再出声 review、再往下走：
  - 动手前一句话（“我让 AI 实现 Order 类的输入校验”）；
  - 生成后出声验（“这版对了，判空 + 校验数量，正是我要的” / “不对，它抛异常而代码库惯例是返回 error 对象，我要 reprompt” / “这段很多，我先读一遍确认”）。
- 不用逐行讲，但决策要讲（为什么选这 approach、输出是否符合预期、下一步干什么）。active coding 时约 30–60 秒一句话。
- 等 AI 时别静默盯 spinner：讲思路（为什么选这个算法、预期生成代码怎么工作），或并行干活（读下一步要用的代码、草拟当前步的测试、想 edge case）。
- 卡住直接问面试官（“cycle 怎么处理我卡住了，你有什么建议吗”）是协作，不是示弱；转向要说原因（“这 approach 时间复杂度扛不住大输入，我换 heap”）。面试官评的是你进死角后认出 + 恢复的速度，不是你避开所有死角。

## 前 5 分钟清单（每道题开局照着走）

1. **定向（5–10 分钟）**：入口 → 核心函数 → 类和数据模型 → 已有测试。先自己读，再问 AI 具体问题。
2. **定验收**：done 的标准是什么？数据模型 + API 契约先于功能；测试策略先定。
3. **拆 3–5 步**：写进 prompt 文档，保持 living 状态；只因新信息改计划，不因 AI 建议改。
4. **先写测试**：对着要建的接口写（函数名 + 输入输出），先失败；和面试官对齐用例。
5. **出声开局**：一句话说意图，再 prompt。

## 两个小例子

### 例 1：读代码（F1 / F7）
场景：刚拿到一个陌生代码库，里面有个 `OrderProcessor`。
- ❌ “解释一下这个代码库。”——太宽泛，AI 会泛泛而谈，还可能把“应该做什么”说成“在做什么”。
- ✅ 先自己扫 5 分钟：入口是 `main` → `OrderProcessor.process(order)` → 用 `OrderValidator` + `InventoryClient`。再问三个具体问题：
  1. “`process` 里先校验还是先扣库存？标行号。”
  2. “库存不足时返回什么？是抛异常还是返回 error 对象？”
  3. “`OrderValidator` 的规则从哪来？是 hardcode 还是读配置？”
- 每个答案自己对着行号核一遍，尤其是第 2 个（异常 vs error 对象是代码库惯例，AI 容易按教科书默认答错）。

### 例 2：找 bug（F4 / F5）
场景：`calculateDiscount(price, coupons)` 测试失败。
- ❌ “帮我找这个函数的 bug。”——Meta 的 AI 不主动指 bug，这样问基本拿不到有用的答案。
- ✅ 先自己复现：输入 `price=100, coupons=["SAVE10","SAVE20"]`，预期 `70`，实际 `80`，测试在第 12 行失败，输出是 `...`。再加自己的怀疑：“我怀疑是第二个 coupon 没叠加上，循环里是不是提前 return 了，帮我看看这段逻辑。”
- AI 确认后，自己修，跑全套回归，再往下走。

## 和传统 coding 轮的区别
- AI Coding 轮里 AI 是加分项：会用 AI（按上面 7 条）本身就是被考的技能。
- 传统 coding 轮没有 AI，基本功要自己练：二分模板、DP 状态、图遍历这些必须冷启动能写，不能依赖 AI。
- 两边共通：测试先行、edge case、复杂度分析、把思路讲清楚——这些不靠 AI。

## 练习题（6 个场景，每次练 1 个，30–60 分钟）

| 编号 | 场景 | 练什么 |
|---|---|---|
| AC1 | 读代码定向：给一段陌生的小型 in-memory KV store 代码，5 分钟内说出入口、核心函数、数据模型，再问 AI 三个具体问题并核行号 | R2 |
| AC2 | 修 bug（Meta Structured 风格）：starter code 里有个 bug，先复现（输入 / 预期 / 实际）+ 自己的假设，再问 AI，修完跑全套回归 | R6 |
| AC3 | 测试先行（Shopify BYOE 风格）：先写测试（七类清单）再让 AI 实现，测试驱动；核心用例写完后让 AI 补 corner 测试，但要细审 | R3、R5 |
| AC4 | Prompt 粒度：同一个功能写两版 prompt（模糊版 vs what+how 给清版），对比 AI 输出，体会粒度杠杆 | R4 |
| AC5 | 坏输出验收：给一段 AI 生成的 150 行代码，找出四类坏输出（training bias / 啰嗦 / 设计走捷径 / 正确性走捷径） | R6 |
| AC6 | 双线沟通：录自己带 AI 解题的过程，回看哪段沉默太久、哪段讲废话（F13 练法）；目标是 30–60 秒一句话 | R7 |

练法：每次练完把 prompt 记录 + AI 输出 + 你的 review（哪里对、哪里错、为什么）贴回 AI coding mock 对话，我逐道指正。重点看三处：计划有没有先行、验证有没有小步做、出声有没有跟上。
